[编号260919-2]问：


	插件当前的 AI 推理 API 配置需要从客户端迁移到服务端统一管理，插件本身不再直接保存各上游平台的 API Key、Base URL 等敏感配置。

	服务端管理的上游不一定都是直接接入大模型厂商，也可能是第三方云平台、API 聚合平台或自建中转平台，因此服务端需要采用统一的“渠道 + 模型”抽象进行管理。

	客户端登录后，可以从服务端获取当前用户有权限使用的 AI 渠道及模型列表，并按照渠道分组展示模型 ID，供用户选择实际调用的模型。

	用户登录方式采用手机号 + 验证码。用户在插件中输入手机号后，登录验证码可以通过微信公众号私信或微信服务通知下发。

	用户注册流程暂时保持简单，不需要设计复杂的注册系统。用户直接关注指定公众号，并向公众号发送如下格式的消息：

	`reg:15911111111`

	服务端识别该消息后，即为对应手机号创建用户，完成注册。当前仅面向小范围用户使用，因此先采用这种轻量方式。

	后台需要提供用户管理和 AI 使用管理能力，包括：

	* 查看每个用户在指定时间范围内的 AI 调用次数、Token 消耗、费用或其它可统计的用量数据。
	* 单独启用或暂停某个用户的 AI 推理权限。
	* 为不同用户灵活配置允许使用的 AI 渠道。
	* 进一步限制某个用户在指定渠道下具体可以使用哪些模型。

	服务端计划部署在 Cloudflare 平台，可能会用到Workers、Workflows、静态托管Pages、对象存储R2、数据库D1、AI Gateway & Worker AI、本地部署用Wrangler CLI  可以参考：
	https://www.youtube.com/watch?v=3MxhQGFpjro （"赛博大善人"CloudFlare，这些也全都免费？！）

	需要特别注意：这个服务端必须与 Temu 插件的具体业务完全解耦。

	它的职责仅限于提供通用的 AI 推理中转、用户认证、权限控制、渠道/模型管理和用量统计能力。Temu 商品筛选、采集、验证码场景等具体业务逻辑都不应该进入这个服务端。

	后续其它系统也会复用同一套 AI 推理服务，因此整体设计应按照独立、通用的 AI Gateway / AI Proxy 服务来实现。

	另外发现一个项目：

	https://github.com/Wei-Shaw/sub2api

	暂时不确定是否适合直接采用，可以先作为架构设计和实现方式的参考，不必为了使用该项目而强行调整现有设计。

	要求服务端代码保存到server目录，能够使用Wrangler CLI本地测试验证一整套从页面到数据库、存储、AI等。
