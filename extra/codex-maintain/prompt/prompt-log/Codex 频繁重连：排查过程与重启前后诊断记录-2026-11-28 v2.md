# Codex 频繁重连：排查过程与重启前后诊断记录

记录日期：2026-11-28（Asia/Singapore）

本记录根据对话及用户提供的两份完整 `doctor` 报告整理。两份完整原文保存在文末；报告本身未给出完整的检查时间，因此这里不推测每一步的具体时间。

## 1. 问题、环境和处理要求

Windows 上的 Codex 桌面端经常出现“正在重新连接 5/5”。用户要求排查并提出解决办法，同时保留高级功能、测试功能、沙盒、插件和技能等功能。

本机使用 Trojan-Qt5，用户提供的本地代理端口如下：

| 用途 | 地址 |
| --- | --- |
| HTTP / HTTPS 代理 | `http://127.0.0.1:58591` |
| SOCKS5 代理 | `socks5://127.0.0.1:51837` |

用户给出的类 Unix shell 环境变量示例为：

```bash
export HTTP_PROXY=http://127.0.0.1:58591
export HTTPS_PROXY=http://127.0.0.1:58591
export ALL_PROXY=socks5://127.0.0.1:51837
```

本次最终使用 Windows 系统代理和 Codex 的 `respect_system_proxy` 设置。诊断报告中代理环境变量一直显示 `none`，并不妨碍启用系统代理。

## 2. 定位桌面端附带的程序

用户在 PowerShell 运行 `codex doctor` 时，PowerShell 报 `CommandNotFoundException`：没有找到名为 `codex` 的命令。此前助手先建议切换工作目录、并提到安装独立 CLI，未直接回答桌面端程序位置，属于判断失误。

用户之后通过下面的 PowerShell 命令查找桌面端释放的程序并运行完整诊断：

```powershell
$exe = Get-ChildItem "$env:LOCALAPPDATA\OpenAI\Codex\bin" -Filter codex.exe -File -Recurse -ErrorAction SilentlyContinue |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 1 -ExpandProperty FullName

if ($exe) { & $exe doctor } else { "这个位置没找到桌面端的 codex.exe" }
```

两次完整报告均显示同一程序和版本：

```
C:\Users\FF\AppData\Local\OpenAI\Codex\bin\9e1da79431da526b\codex.exe
Codex Doctor v0.167.0-alpha.4.1 · windows-x86_64
```

查找命令按修改时间选择文件；程序所在的编号目录可能随桌面端更新而变化。仅按修改时间选择也不能保证未来每次均为桌面端实际正在使用的版本。

## 3. 首次完整诊断：修改配置及重启前

汇总为：

```
21 ok · 1 idle · 3 notes · 3 warn · 0 fail degraded
```

有三项警告：Responses WebSocket 握手超时、`node_repl` MCP 可选环境变量提示、会话文件与状态数据库之间的不一致。

### 3.1 WebSocket 和代理

```
proxy env vars           none
respect system proxy     disabled
supports websockets      true
connect timeout          15000 ms
handshake timed out
```

报告提示 HTTPS 回退可能仍然可用；它没有证明回退一定成功。普通 HTTP 可达性检查中，ChatGPT 推理地址返回 `HTTP 405`、桌面端资源 CDN 返回 `HTTP 200`。`405` 表示该次探测收到响应，不等于推理请求及 WebSocket 长连接正常。

结合本机需要代理、诊断进程没有代理环境变量且未启用系统代理的证据，未使用预期代理被列为优先排查方向；当时不能断言它是所有重连的唯一原因。

### 3.2 会话与索引

报告显示活动 rollout 文件 57 个、归档文件 3 个，数据库中共 58 行，其中活动行 55、归档行 3。问题计数为：

```
rollout DB missing active rows       11
rollout DB stale rows                 9
rollout DB duplicate rollout thread ids  2
```

报告同时指出有 rollout 文件未记录在状态数据库，以及数据库记录指向缺失或不可用的 rollout 文件；不要把 `missing active rows` 简单解释成“数据库有 11 行缺少文件”。数据库完整性检查本身为 `ok`。报告建议附上 `doctor` 报告向支持人员反馈。详情和样本路径见文末原文。

### 3.3 MCP

诊断发现一个已启用的 stdio MCP 服务 `node_repl`，并提示下列变量在诊断进程中未设置：

```
BROWSER_USE_ACCESS_EXECUTOR_ID
BROWSER_USE_ACCESS_PIPE_PATH
BROWSER_USE_ACCESS_VERIFYING_IDENTITY
CODEX_WINDOWS_REGISTERED_CORE
```

诊断标为可选问题。由于报告从独立 PowerShell 进程生成，不能据此断定桌面端相关工具运行时也缺少这些变量，也不能认定它们造成重连。没有禁用该 MCP 或手工填入变量。

### 3.4 沙盒和其他状态

- 沙盒为受限文件系统、受限网络，审批策略 `OnRequest`；后端为 `elevated`，配置已完成。
- 配置文件解析成功，ChatGPT 认证已配置。
- 可用磁盘空间约 12.6 GiB，报告阈值为 5 GiB 警告、1 GiB 失败。
- 诊断工作目录为 `C:\Users\FF`，报告没有识别到该目录属于 Git 工作区；这不能单独说明用户项目有问题。
- 报告识别到桌面端版本 `26.1120.6357.0`，但 `running` 显示 `false`；这是诊断工具当时的识别结果，不能单独证明桌面端没有运行。
- `app-server not running (ephemeral mode)` 被标为空闲，而非失败。
- 更新部分列出 `0.172.0`，又显示 `current version is not older`；这一显示差异没有进一步核实，也没有据此更新。

## 4. 核对系统代理并修改配置

只读检查 Windows 当前用户系统代理时得到：

```
ProxyEnable  1
ProxyServer  127.0.0.1:58591
```

因此，当时 Windows 已启用系统代理并指向 Trojan-Qt5 的 HTTP 端口。尝试通过当前执行环境读取本机 TCP 监听状态时，系统返回无法访问 CIM 资源，不能从该检查得出端口是否监听的结论；随后由用户自行执行的连接测试提供了证据。

用户在 `C:\Users\FF\.codex\config.toml` 的已有 `[features]` 段中自行添加：

```toml
respect_system_proxy = true
```

只读复核显示：

```
70: [features]
72: respect_system_proxy = true
```

该设置让 Codex 原生运行程序可以使用操作系统代理处理自身网络请求。官方说明它不覆盖每个桌面端请求、浏览器请求、插件进程或 shell 命令：OpenAI 系统代理配置说明。本次没有以解决网络问题为由关闭沙盒、插件、技能或其他功能；但 `doctor` 也没有逐项验证这些功能。

## 5. 代理连通性和配置生效检查

### 5.2 HTTP 系统代理

### 6.2 已解决和尚未确认的部分

- *已观察到的改善：**新启动的 `doctor` 在启用系统代理后两次建立了 Responses WebSocket 连接，完整报告中的 WebSocket 超时警告消失。用户的 HTTP 和 SOCKS5 代理端口也分别通过了普通 HTTPS 请求检查。
- *尚不能确认：**这些诊断是独立进程、时间点上的检查，且报告明确未检查活动会话覆盖配置。它们不能证明桌面端长时间任务永不掉线，也不能证明所有“正在重新连接 5/5”均由同一原因造成。需要在重启后按原有工作方式持续观察，特别是之前容易触发问题的长任务。
- *仍有的警告：**会话文件与数据库索引不一致、`node_repl` 的四个环境变量提示。它们在重启后都仍存在，目前没有证据证明它们导致网络重连。

## 7. 后续建议

1. 保持 Trojan-Qt5 和 Windows 系统代理正常运行，在已重启的桌面端按平时工作方式观察。如果不再频繁重连，可认为实际体验得到改善；长连接仍应根据持续使用结果判断。
2. 若再次频繁出现“正在重新连接 5/5”，记录发生时间、使用的 Trojan 节点、任务是否最终完成，再结合桌面端当时的日志排查代理链路、长连接及其他原因。
3. 如历史会话有缺失或无法打开，先保护现有会话和数据库，针对报告中的文件路径、状态及可能的重复记录做只读核对；报告建议携带诊断结果向支持人员反馈。
4. 如浏览器或相关插件出现实际错误，再结合具体错误排查 MCP 环境变量；不要仅因独立 `doctor` 的提示关闭 MCP、插件或技能。

本记录基于诊断结果和用户提供的测试结果。未对所有高级功能、插件、技能做逐项功能测试，也未确认长时间重连问题彻底消失。

| provider / API / 认证 | `openai`、`responses`、ChatGPT | 相同 | 同一类诊断目标；完整地址在报告中脱敏。 |
| DNS | `1 IPv4, 0 IPv6, first IPv4` | 相同 | 是报告时的 DNS 结果，不能据此确认所有请求的 DNS 解析位置。 |
| `reasoning header`、`server model present` | 超时前无成功握手结果 | 均为 `false` | 这是成功握手后显示的字段；报告未将它们单独列为警告，不能据此认定推理功能缺失。 |
| HTTP 可达性 | ChatGPT 推理地址 `405`，资源 CDN `200` | 相同 | `405` 表示探测请求收到 HTTP 响应；不是完整推理请求的成功证明。 |
| 后台服务 | `not running`，`ephemeral mode`；对应配置及 PID 文件缺失 | 相同 | 被标为 `idle`；不能把未运行的持久守护进程等同于桌面端不可用。 |

### 9.6 下一次复发时如何收集可比较的证据

1. 记录出现“正在重新连接 5/5”的本地日期和时间、当前使用的 Trojan 节点，以及任务最终是恢复、失败还是仍在运行。不要在任务状态未知时反复重新提交。
2. 保持当时的代理配置，运行同一个桌面端程序的 `doctor --network-only`，记录 WebSocket 是成功、超时还是其他错误；如果桌面端版本更新，应先重新核对实际程序路径。
3. 对比同时段普通 HTTP 代理请求与 WebSocket 诊断，区分普通 HTTPS、握手和持续长连接；每次检查只能证明相应时刻及相应请求的结果。
4. 根据具体时间只读检查桌面端相关日志；报告中的 `running false` 和 `active thread overrides not inspected` 表明不能只凭独立诊断断言桌面端有效配置。分享日志前检查会话内容、路径、Cookie 与其他敏感信息。
5. 若排查会话索引，先核对相关文件是否存在及数据库中对应路径，保留原始数据；在确认数据关系与恢复方案前不要删除、合并或重建索引。
